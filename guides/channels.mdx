waybill-arc sends RFQs to suppliers through a unified messaging layer in `src/channels/`. Each channel client (email via AgentMail, voice and SMS via Vapi, WhatsApp via the Meta Cloud API, and the supplier simulator) implements the same `ChannelClient` contract. `src/channels/index.ts` is the only surface callers touch, so inbound replies and outbound sends share one interface regardless of the underlying provider.

## Unified channel API

```typescript
import { getThread, sendMessage, sendMessages } from "./channels/index.js";

// Send a single message to one supplier
await sendMessage({
  requestID: "299cb5b9-4b9d-4c1a-9d51-3f2f0a4f0e21",
  supplierID: "SUP-00142",
  channel: "email",
  message: "Please quote 2000 units of STM32F103C8T6...",
});

// Broadcast the same message to multiple suppliers on one channel
await sendMessages({
  requestID: "299cb5b9-4b9d-4c1a-9d51-3f2f0a4f0e21",
  channel: "email",
  supplierIDs: ["SUP-00142", "SUP-00187"],
  message: "Please quote 2000 units of STM32F103C8T6...",
});

// Retrieve the provider thread for a given supplier and channel
const thread = await getThread({
  requestID: "299cb5b9-4b9d-4c1a-9d51-3f2f0a4f0e21",
  supplierID: "SUP-00142",
  channel: "email",
});
```

## Registering supplier contacts

Before sending on any channel, register the supplier’s address in the `supplier_contacts` table. Use an upsert so updates overwrite existing entries.

```sql
INSERT INTO supplier_contacts (supplier_id, channel, address)
VALUES
  ('SUP-00142', 'email', 'sales@supplier.example'),
  ('SUP-00142', 'voice', '+14155550123'),
  ('SUP-00142', 'sms', '+14155550123'),
  ('SUP-00142', 'whatsapp', '14155550123')
ON CONFLICT (supplier_id, channel) DO UPDATE SET address = EXCLUDED.address;
```

WhatsApp addresses are stored as digits only (`14155550123`). The client strips anything else, so a `+`-prefixed row also works.

## Threads

`channel_threads` maps `(request_id, supplier_id, channel)` to the provider thread so replies stay in-thread and inbound webhooks can recover the request context.

- For `voice`, the thread is the most recent Vapi call ID.
- For `sms`, the thread is the Vapi session ID.
- For `email`, the thread is managed by AgentMail.
- For `whatsapp`, the thread is the supplier's `waId` (their WhatsApp number). When several requests share the same `waId`, an inbound reply resolves to the most recently created request.

## Email (AgentMail)

To receive email replies, point AgentMail at `POST /webhook/email` and store the printed webhook secret as `AGENTMAIL_WEBHOOK_SECRET`.

```bash
npm run channels:register-webhook -- https://your-host/webhook/email
```

Required environment variables:

| Variable | Description |
| --- | --- |
| `AGENTMAIL_API_KEY` | AgentMail API key |
| `AGENTMAIL_WEBHOOK_SECRET` | Svix signing secret for inbound email |
| `AGENTMAIL_INBOX_ID` | Use an existing inbox instead of creating one |
| `AGENTMAIL_INBOX_USERNAME` | Username for the shared inbox (default: `procurement`) |

## Voice (Vapi)

Vapi needs no webhook registration step. Every call creates a transient assistant carrying `server.url` and `server.headers`, so setting `VAPI_WEBHOOK_URL` and `VAPI_WEBHOOK_SECRET` is enough for `POST /webhook/vapi` to start receiving events.

A voice call delivers the message to the supplier, falls back to voicemail if unanswered, and fires `end-of-call-report` when the call ends. That event resumes the supervisor automatically. `getThread` reconstructs the conversation from the call transcript.

Required environment variables:

| Variable | Description |
| --- | --- |
| `VAPI_API_KEY` | Vapi API key |
| `VAPI_PHONE_NUMBER_ID` | Vapi phone number placing outbound calls |
| `VAPI_WEBHOOK_URL` | Public URL of `POST /webhook/vapi` |
| `VAPI_WEBHOOK_SECRET` | Shared secret echoed back as `x-waybill-signature` |

## SMS (Vapi)

SMS uses the same Vapi integration but with additional constraints.

<Warning>
  SMS is constrained by Vapi and Twilio requirements:

  - It requires a 10DLC-approved US Twilio number imported into Vapi (`VAPI_SMS_PHONE_NUMBER_ID`).
  - Outbound SMS to non-US numbers works, but inbound SMS is US↔US only. A non-US supplier cannot reply through Vapi.
  - Vapi’s own assistant auto-answers inbound SMS before the supervisor sees it.
  - Resuming on an SMS reply relies on the `session.updated` event, which is unverified against a live 10DLC number. Polling `getThread` remains the reliable path, so an SMS RFQ still works even if the event never arrives.
</Warning>

Required environment variables:

| Variable | Description |
| --- | --- |
| `VAPI_API_KEY` | Vapi API key |
| `VAPI_SMS_PHONE_NUMBER_ID` | SMS-enabled US Twilio number imported into Vapi |
| `VAPI_WEBHOOK_URL` | Public URL of `POST /webhook/vapi` |
| `VAPI_WEBHOOK_SECRET` | Shared secret echoed back as `x-waybill-signature` |

## WhatsApp (Meta Cloud API)

The `whatsapp` channel talks to the Meta WhatsApp Cloud API directly. waybill-arc owns the Meta credentials and the message store: a Prisma-managed `whatsapp` Postgres schema at `WHATSAPP_DATABASE_URL` that holds contacts, messages, status history, and idempotency keys. See [Database setup](/configuration/database) for the migration commands.

Configuration is all-or-nothing. Set none of the variables to disable the channel, or set all seven required ones:

| Variable | Default | Description |
| --- | --- | --- |
| `WHATSAPP_ACCESS_TOKEN` | — | Meta System User token for the Cloud API |
| `WHATSAPP_PHONE_NUMBER_ID` | — | Numeric phone number ID (not the phone number) |
| `WHATSAPP_BUSINESS_ACCOUNT_ID` | — | The WhatsApp Business Account (WABA) ID |
| `WHATSAPP_APP_SECRET` | — | Verifies `x-hub-signature-256` on the Meta webhook |
| `WHATSAPP_WEBHOOK_VERIFY_TOKEN` | — | Echoed in the Meta webhook GET handshake |
| `WHATSAPP_API_KEY` | — | Bearer key protecting the `/api/*` channel endpoints |
| `WHATSAPP_DATABASE_URL` | — | Postgres holding the `whatsapp` schema (message store) |
| `WHATSAPP_DIRECT_URL` | — | Optional non-pooled URL used by `prisma migrate` |
| `GRAPH_API_BASE_URL` | `https://graph.facebook.com` | Graph API host |
| `GRAPH_API_VERSION` | `v26.0` | Graph API version |

### Meta webhook setup

Point your Meta app's webhook at `https://your-host/webhook/whatsapp`:

- The `GET` verification handshake echoes `hub.challenge` when `hub.verify_token` matches `WHATSAPP_WEBHOOK_VERIFY_TOKEN`.
- `POST` events are verified against `WHATSAPP_APP_SECRET` via the `x-hub-signature-256` header.

Inbound messages are persisted to the message store, then dispatched in-process to the agent. The thread is looked up by the sender's `waId` and redeliveries are deduped on the thread's last recorded message ID. Any failure returns `500` so Meta redelivers. See [Webhooks](/guides/webhooks) for the full endpoint behavior.

### 24-hour service window

<Warning>
  Meta only allows free-form messages within 24 hours of the supplier's last inbound message. Outside that window, a free-form text fails with Meta error `131047`, which arrives as a status event after the send is accepted. It never surfaces to the agent as an HTTP error. Use an approved template to reach a supplier outside the window.
</Warning>

### Channel API

The full WhatsApp channel API (messages, conversations, media, templates, phone number, business profile, setup) is exposed under `/api/*`. Every route requires `Authorization: Bearer <WHATSAPP_API_KEY>` (or `X-API-Key`) and returns `503` when the channel is unconfigured.

```bash
curl -X POST http://localhost:3001/api/messages \
  -H "Authorization: Bearer $WHATSAPP_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "to": "14155550123", "type": "text", "text": { "body": "hello" } }'
```

The response includes `serviceWindowOpen`: `false` when the recipient is outside the 24-hour service window (free-form sends will fail, so use a template) and `null` when the recipient has never messaged in.

For how inbound webhooks resume the supervisor, see [Webhooks](/guides/webhooks). For the full list of environment variables, see [Environment Variables](/configuration/environment).
